# Архитектурное решение (ADR): Переход на Event-Driven архитектуру на базе Apache Kafka (InsureTech)

## 1. Контекст и проблематика (As-Is)
Текущая архитектура базируется на синхронном REST-взаимодействии и периодическом polling-е. `ins-product-aggregator` опрашивает 5 страховых компаний синхронно. `core-app` запрашивает агрегатор раз в 15 минут, а `ins-comp-settlement` делает тяжелый запрос реестра раз в сутки.

**Проблемы при росте до 10+ партнеров:**
* **Latency и отказоустойчивость:** Агрегация ограничена самым медленным партнером. Отказ одного API партнера ведет к сбою всего процесса агрегации (504 Gateway Timeout).
* **Staleness:** Окно обновления в 15 минут / 24 часа приводит к неактуальным тарифам и финансовым расхождениям.
* **Пиковые нагрузки:** Суточный батч-запрос перегружает базу данных `core-app` и сеть.

---

## 2. Целевая архитектура (To-Be)
Внедрение кластера **Apache Kafka** в качестве центральной шины данных (Event Bus). Переход от модели "Pull" (опрос) к модели "Push" (реакция на события).

* `ins-product-aggregator`: Выступает в роли **Producer**. Опрашивает партнеров в фоне и непрерывно публикует обновления продуктов.
* `core-app`: Выступает **Consumer**-ом для обновления тарифов, и **Producer**-ом для публикации событий оформления страховок.
* `ins-comp-settlement`: Выступает **Consumer**-ом для актуализации справочников и накопления реестра проданных страховок в реальном времени.

---

## 3. Решение по интеграции Apache Kafka (Дизайн)
Для обеспечения строгой очередности сообщений, масштабируемости и консистентности применяются следующие архитектурные паттерны Kafka:

### 3.1. Архитектура топиков (Topics & Partitioning)
1.  **Топик `insurance.products.updated.v1`**
    * **Назначение:** Передача актуальных тарифов и условий от агрегатора.
    * **Ключ партицирования (Message Key):** `product_id` (или `partner_id`). Гарантирует, что все обновления цены одного конкретного продукта всегда будут попадать в одну партицию и обрабатываться строго последовательно.
    * **Стратегия хранения (Retention):** Настройка **Log Compaction**. Kafka будет бесконечно хранить последнее актуальное состояние (слепок) каждого `product_id`. Если `core-app` или `settlement` перезапустятся с пустой БД, они смогут мгновенно "вычитать" актуальный прайс-лист из топика, не дожидаясь новых опросов партнеров.

2.  **Топик `insurance.policies.issued.v1`**
    * **Назначение:** Передача данных об оформленных полисах из `core-app` в `ins-comp-settlement`.
    * **Ключ партицирования:** `policy_id`.
    * **Стратегия хранения:** Временная (например, 7-14 дней), так как сервис взаиморасчетов консюмит эти события и надежно сохраняет их в свою СУБД.

### 3.2. Consumer Groups (Группы потребителей)
Каждый сервис работает в своей независимой консюмер-группе, реализуя паттерн Publish-Subscribe:
* `core-app-group` — читает обновления продуктов для витрины.
* `settlement-group` — читает и обновления продуктов, и оформленные полисы.
* **Масштабирование:** При увеличении нагрузки (например, при распродажах страховок), оркестратор (Kubernetes) может поднять дополнительные реплики `core-app`. Kafka автоматически перебалансирует партиции внутри `core-app-group` между новыми подами, распараллелив чтение.

### 3.3. Схемы данных (Schema Registry)
Для предотвращения сбоев при изменении структур данных внедряется **Kafka Schema Registry** (формат Avro или Protobuf). Это гарантирует строгую типизацию: `core-app` не упадет с ошибкой парсинга, если агрегатор случайно изменит формат JSON.

---

## 4. Гарантия доставки: Transactional Outbox
Для надежной отправки данных об оформленных страховках из `core-app` в Kafka применяется паттерн Transactional Outbox (решение проблемы Dual Write).

1.  **Транзакция БД:** При оформлении полиса `core-app` открывает транзакцию в PostgreSQL. Он сохраняет полис в таблицу `policies` и одновременно формирует событие в таблицу `outbox_events`. Транзакция коммитится атомарно.
2.  **Message Relay (Kafka Connect):** Специализированный коннектор (например, **Debezium CDC**) читает транзакционный лог PostgreSQL (WAL) и гарантированно перекладывает события из таблицы `outbox_events` в топик `insurance.policies.issued.v1`.
3.  **Семантика:** Это обеспечивает доставку событий в Kafka с гарантией *At-Least-Once*, полностью исключая риск того, что клиент оплатил страховку, а система взаиморасчетов об этом не узнала.

---

## 5. Вывод
Интеграция Apache Kafka решает проблему "бутылочного горлышка" синхронных API. Использование компактизации логов (Log Compaction) решает проблему "холодного старта" кэшей, а внедрение Transactional Outbox с CDC (Change Data Capture) гарантирует 100% доставку финансовых данных для `ins-comp-settlement` без тяжелых ночных выгрузок.
